# Архитектура «ПДД Тренер»

## Слои

```
            ┌────────────── src/web (SPA) ───────────────┐   ┌──── src/server (REST API) ────┐
            │ views.ts — чистые функции → SafeHtml       │   │ app.ts — маршруты, auth,       │
            │ main.ts  — события, таймер, навигация      │   │ rate-limit, problem+json       │
            └───────────────┬────────────────────────────┘   └──────────────┬────────────────┘
                            │                                               │
                  src/app (TrainerService, порты)                 src/server/repository.ts
                            │                                    (Memory / File / → PostgreSQL)
            ┌───────────────┴─────────────── src/core ──────────────────────┴───────────────┐
            │ exam.ts · session.ts · progress.ts · srs.ts · adaptive.ts · stats.ts          │
            │ question-bank.ts · validation.ts · rng.ts · types.ts   (без I/O, без DOM)     │
            └───────────────────────────────────┬───────────────────────────────────────────┘
                                         src/content (банк, темы, категории, SVG-знаки, импорт)
```

Правила зависимостей проверяются тестом `tests/content.test.ts → Архитектурные ограничения`:
ядро не импортирует ничего, кроме себя; `content` и `app` не знают о Node, вебе и сервере; веб не тянет серверный код.

## Ключевые решения (ADR)

| № | Решение | Почему | Цена |
|---|---|---|---|
| 1 | **Функциональное ядро**: состояния сессий — неизменяемые сериализуемые объекты, переходы — чистые функции | Одна и та же логика экзамена работает в браузере, на сервере и в тестах; сессия переживает перезагрузку и хранится в БД как JSON | Немного больше копирований (пренебрежимо: ≤ 800 элементов) |
| 2 | **Сидируемый ГСЧ** (mulberry32) с сохранением состояния в экзамене | Экзамены воспроизводимы; доп. вопросы после сериализации те же; Monte-Carlo тесты детерминированы | — |
| 3 | **Правила экзамена как конфиг** (`ExamRules`) | Регламент МВД меняется → меняем данные, а не алгоритм; каждое правило покрыто тестом | — |
| 4 | **Контент как данные** (`ContentPack`) с валидацией | Билеты обновляются (обычно 1 марта / 1 сентября) без релиза кода; официальный банк подключается импортом | Нужен импортёр под формат источника |
| 5 | **Знаки рисуются кодом** (SVG) | Нет проблем с правами на картинки, чёткость на любом экране, вес — байты | Схематичность изображений |
| 6 | **Без runtime-зависимостей**, UI без фреймворка | Бандл ~110 КБ вместе с контентом, нет уязвимостей цепочки поставок, мгновенный старт офлайн | Для большого UI в будущем — React/React Native поверх того же ядра |
| 7 | **Офлайн-first + синхронизация слиянием** (`mergeProgress` коммутативна и идемпотентна) | Ученик занимается без сети на нескольких устройствах; конфликтов «кто последний — тот прав» нет | Удаление из избранного разрешается по времени последнего изменения |
| 8 | **Анти-чит на сервере**: правильные ответы не отдаются клиенту до конца экзамена, время считается сервером | Результаты серверного экзамена можно показывать автошколе | Экзамен на сервере требует сети |
| 9 | **Порт хранилища асинхронный** | Файловый адаптер для одного инстанса, PostgreSQL — без изменений API-слоя | — |

## Правила экзамена (как реализованы)

| Правило ГИБДД | Где в коде | Тест |
|---|---|---|
| 20 вопросов, 4 блока × 5, 20 минут | `createExam` | «20 уникальных вопросов…» |
| Ошибка в блоке → +5 вопросов того же блока, +5 минут | `answerExam` + `pickExtraQuestions` | «одна ошибка → +5 вопросов…» |
| Доп. вопросы — в первую очередь той же темы | `pickExtraQuestions` | «доп. вопросы в первую очередь той же темы…» |
| 2 ошибки в одном блоке → не сдан | `answerExam` (`block_errors`) | «две ошибки в одном блоке…» |
| Более 2 ошибок → не сдан | `answerExam` (`total_errors`) | «три ошибки в разных блоках…» |
| Ошибка в доп. вопросе → не сдан | `answerExam` (`extra_error`) | «ошибка в дополнительном вопросе…» |
| Время истекло → не сдан | `tickExam`, проверка в `answerExam` | «истечение времени…» |

Плюс property-тест на 500 случайных экзаменов проверяет согласованность структуры, времени и вердикта,
а Monte-Carlo тест сверяет аналитическую формулу вероятности сдачи (`passProbability`) с реальным движком.

## Вероятность сдачи

Для каждого блока оценивается вероятность верного ответа `p_b` (сглаженная доля верных ответов по вопросам блока,
незнакомые вопросы — со штрафом). Затем точно по правилам: в блоке либо 0 ошибок (`p^5`), либо 1 ошибка и 5 верных
доп. вопросов (`5·p^4·(1−p)·p^5`); динамикой по числу ошибок суммируются исходы, где ошибок ≤ 2.

## Качество

| Проверка | Команда |
|---|---|
| Строгая типизация (TS 7, `strict`, `noUncheckedIndexedAccess`, `erasableSyntaxOnly`) | `npm run typecheck` |
| Валидация контента | `npm run validate:content` |
| Unit + property + контент + архитектура + рендер UI + интеграционные тесты API | `npm test` |
| Покрытие | `npm run test:coverage` |
| Всё вместе (то же, что на CI) | `npm run check` |
